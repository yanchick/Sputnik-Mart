## Основные принципы

### I. Контракты прежде кода (NON-NEGOTIABLE)

- Границы сервисов и данных описываются типизированными контрактами до написания реализации.
- Запросы и ответы REST — только Pydantic v2-модели; OpenAPI-схема генерируется из кода и служит источником истины для клиентов.
- События описываются контрактами AsyncAPI с явной версией и политикой совместимости.
- Обратно несовместимое изменение контракта допускается только через новую версию и план миграции.
- Контракты проверяются автоматически: schemathesis для REST, схемы событий — в контрактных тестах.

Обоснование: единый контракт исключает рассинхрон между сервисами, генераторами и DAGами и делает интеграцию проверяемой машинно.

### II. Асинхронность по умолчанию и единый рантайм

- Единый рантайм: Python 3.12 и uv (пакеты, src-layout); одни и те же практики для сервисов, DAGов и генераторов.
- Весь I/O асинхронный: FastAPI + Starlette (Uvicorn/Gunicorn), SQLAlchemy 2.0 (async) + asyncpg, httpx (+httpx-sse), aiokafka.
- Блокирующие вызовы в async-контуре запрещены без явного выноса в executor.
- Конфигурация задаётся только через pydantic-settings и переменные окружения; секреты не хранятся в коде.

Обоснование: единый рантайм снижает стоимость владения, а async-first контур удерживает задержки и потребление ресурсов под нагрузкой.

### III. Слоёные данные и контроль качества (NON-NEGOTIABLE)

- Поток данных строится по медальон-схеме bronze → silver → gold; переход между слоями возможен только после успешной валидации.
- Схемы слоёв описываются Pandera; проверки аномалий и отчёты — Great Expectations.
- Целевой формат хранения — Parquet (PyArrow); обработка — pandas и Polars.
- Запись идемпотентна: детерминированные ключи и партиции, upsert, повторный запуск не создаёт дублей.
- Неконформные записи не попадают в следующий слой: они уходят в карантин или DLQ с фиксацией причины.
- Аналитические витрины gold строятся в ClickHouse; метаданные провайдеров хранятся в MongoDB (Motor).

Обоснование: контроль на границах слоёв не позволяет дефектным данным просачиваться в аналитику и отчёты, а идемпотентность делает перезапуски безопасными.

### IV. Событийная надёжность и идемпотентность

- Обмен событиями — через Redpanda (Kafka API): топики commerce.*, sensors.readings*, DLQ.
- Модель доставки at-least-once; каждый консьюмер обязан быть идемпотентным.
- Ключи дедупликации и идемпотентности хранятся в Redis; там же — rate-limit и сессии.
- Ретраи выполняются с backoff; «ядовитые» сообщения после исчерпания попыток уходят в DLQ.
- Эволюция схем должна быть совместимой (backward/forward); несовместимое изменение — только новый топик или версия.

Обоснование: at-least-once неизбежно даёт повторную доставку, поэтому корректность опирается на идемпотентность, а не на иллюзию exactly-once.

### V. Наблюдаемость и тестируемость по умолчанию

- Логи структурированы (structlog) и несут requestId сквозь все сервисы.
- Трассировка и метрики — OpenTelemetry и prometheus-client; дашборды — Grafana.
- Обязательные метрики: лаг консьюмеров и свежесть данных; по ним настраиваются алерты.
- Тесты: pytest и pytest-asyncio (unit), testcontainers (интеграционные с реальными Postgres, Redis, ClickHouse и Redpanda), schemathesis (контрактные тесты живых сервисов).
- Качество кода: ruff, black, mypy; отклонения не мержатся.

Обоснование: без сквозной наблюдаемости и воспроизводимых тестов невозможны ни отладка распределённого контура, ни доверие к данным.

## Рабочий процесс и шлюзы качества

- Pull request не мержится, если падают ruff/black/mypy, unit- или контрактные тесты либо сборка образа.
- GitHub Actions — единый обязательный шлюз; Docker и docker compose (профили) обеспечивают воспроизводимый запуск стека.
- Изменения схемы БД выполняются только через Alembic; каждая миграция сопровождается планом отката.
- Оркестрация — Apache Airflow 2.9: retries/backoff и сенсоры обязательны для внешних зависимостей.
- Изменение публичного контракта требует обновления спецификаций (OpenAPI/AsyncAPI) и контрактных тестов в том же PR.

## Порядок изменений

- Конституция имеет приоритет над прочими практиками и соглашениями проекта.
- Поправка оформляется PR, который изменяет только `.specify/memory/constitution.md` и содержит Sync Impact Report.
- Версионирование (semver):
  - MAJOR — удаление или переопределение принципа либо нормы, несовместимое с прежним поведением.
  - MINOR — новый принцип или раздел либо существенное расширение правил.
  - PATCH — уточнения, формулировки и исправления без изменения смысла.
- Для MAJOR-поправки обязателен план миграции и обновление зависимых шаблонов и команд.
- Соблюдение проверяется на код-ревью и в CI; несоответствие должно быть устранено либо оформлено явным исключением.
- Runtime-руководство: конституция и шаблоны Spec Kit (`.specify/templates/`) — единственный источник обязательных правил; отдельного guidance-файла нет.
