# Маркетплейс данных — концепция учебного демо-портала (вариант Б)

> Рабочая компания/бренд: **«Спутник Данные»**. Один портал, где маркетплейс данных одновременно является и **витриной** (для базового уровня), и **источником событий пайплайна** (для продвинутого). Развивает и объединяет идею «Спутник Маркет» из [[Семинары — Сквозной пайплайн]].

## Суть варианта

Маркетплейс, где **товар — это сами данные** (потоки городских датчиков, метео, качество воздуха, энергия), а **бизнес маркетплейса** — привычные события (клики, заказы, отзывы), только про покупку и потребление данных.

Внутри портала работают **две нити данных**:

- **Нить товаров (content plane)** — «сырьё», которое продаётся: показания датчиков публикуются провайдерами, проходят валидацию/очистку, складываются в хранилище и отдаются через API.
- **Нить бизнеса (commerce plane)** — как маркетплейс живёт: покупатели листают каталог, оформляют подписки, скачивают, оставляют отзывы о качестве данных. Это ровно те события (`clicks`, `orders`, `reviews`), что уже заложены в семинары продвинутого уровня.

Связывает их **подписка**: покупатель подписывается на поток датчиков → событие заказа уходит по commerce-нити → оркестратор запускает доставку свежих чтений из content-нити покупателю через API.

Преимущество перед исходным «Спутник Маркет»: у товаров-данных **фасад нагляден для базового уровня** (можно бродить по витрине и смотреть живые графики), а под капотом остаётся весь пайплайн для продвинутого уровня.

## Единая схема всего семестра

```
          ФАСАД (видят все: базовый уровень = покупатель)
   ┌────────────────────────────────────────────────────────┐
   │ Витрина каталога │ Живые потоки датчиков │ API+Swagger │
   │ Личный кабинет   │ Страница качества/SLA │ Ноутбуки     │
   └────────────────────────────────────────────────────────┘
                               ▲
         commerce-нитка         │         content-нитка (товары)
   клик/заказ/подписка/отзыв    │   датчики и провайдеры (метео, PM2.5, энергия)
              │                 │                  │
              ▼                 │                  ▼
   ★ Kafka: orders, subs,      │        REST/CSV-выгрузки / ★ Kafka readings
     reviews, downloads        │                  │
              │                 │                  ▼
              └────►  Data Lake (MinIO)  bronze (сырьё) ◄────┘
                              │
                          validate → silver (Pandera/GE)
                              │
                       transform → gold/фичи (временные ряды, сентимент)
                              │
        ┌─────────────────────┴─────────────────────┐
        ▼                                           ▼
   ClickHouse: витрины (метрики          API маркетплейса →
   бизнеса + отдаваемые датасеты)          дашборд покупателя
                              │
                    Airflow оркестрирует обе нити
                    Observability + тестирование + CI/CD + GDPR
```

Один `docker compose`, один репозиторий, одна компания — фасад и машинерия это один и тот же мир.

## Две нити данных

### Нить товаров (content) — что продаём

Потоки «умного города», публикуемые эмуляторами-провайдерами:
- метеостанции (температура, влажность, давление),
- качество воздуха (PM2.5/PM10, шум),
- энергопотребление по зданиям,
- (опционально) транспортные потоки.

Здесь живут «сырые» темы продвинутого уровня: продвинутый сбор, валидация, трансформация, хранилища.

### Нить бизнеса (commerce) — как маркетплейс зарабатывает

- `click` — просмотр карточки датасета / образца,
- `order` / `subscription` — покупка или подписка на поток,
- `download` — выгрузка датасета,
- `review` — отзыв о качестве данных,
- каталог / цены / SLA.

Здесь живут event-системы (Kafka/NATS), оркестрация доставки, GDPR на персональных данных покупателей и метрики бизнеса маркетплейса.

> Ключевой поворот относительно исходной заметки: `order` = подписка на данные, а `review` = оценка качества данных — что **естественно связывается с темой «качество данных»**, а не висит отдельно.

## Маппинг семинаров продвинутого уровня

Семинары 1–10 переносятся почти без изменений, меняются лишь легенда и «продукт», по которому идёт демо.

| Семинар | Концепция | Демо на портале «Спутник Данные» |
| --- | --- | --- |
| 1. Архитектура | Lambda/Kappa, микросервисы | `docker compose`: витрина/API (Postgres каталог) + ClickHouse + MinIO + Kafka + Airflow. Почему commerce и content — разные конвейеры (batch для выгрузок, поток для подписок) |
| 2. Продвинутый сбор | REST/GraphQL, Scrapy, чанки | REST/GraphQL API каталога партнёров-провайдеров; Scrapy парсит «конкурентный маркетплейс» (цены на датасеты); эмулятор датчиков шлёт чтения; партнёрская CSV-выгрузка читается чанками в MinIO |
| 3. Event-системы ★ | Kafka vs NATS | Топики `clicks/orders/reviews` — про маркетплейс данных; топик `readings` — поток датчиков; партиционирование по `user_id`/`station_id`; убиваем консьюмера → at-least-once; окно «подписок за минуту» |
| 4. Валидация/очистка | Pandera/GE, аномалии | GE-suite на сырье датчиков в S3; «битое» показание → DLQ; всплеск PM2.5 через z-score — алерт на **Quality-странице фасада** |
| 5. Трансформация | Фичи, временные ряды, NLP | Часовые агрегаты по станции; прогноз температуры; сентимент **отзывов покупателей о данных** (отзывы = commerce-события + NLP-корпус) |
| 6. Разметка | Label Studio, active learning | Размечаем отзывы покупателей (тот же корпус, что в с/5); kappa между аннотаторами; размеченное возвращается в сентимент-фичи |
| 7. Оркестрация | Airflow | DAGи `ingest_readings`, `deliver_subscription` (событие заказа → доставка свежих чтений), `refresh_quality`; идемпотентность доставки подписок; retry при недоступности провайдера |
| 8. Хранилища | Lake/Warehouse, NoSQL | MinIO bronze/silver; ClickHouse-витрина (отдаваемые датасеты + метрики бизнеса); Mongo — гибкий каталог провайдеров с разной схемой метаданных |
| 9. Observability/DevOps | Мониторинг, тестирование, CI/CD, GDPR | Лаг топика `readings`, свежесть витрины; CI ловит битую схему; GDPR — псевдонимизация покупателей и чистка PII из скачиваний |
| 10. Сводный прогон | Путь события целиком | **Кульминация:** подписка на метеостанцию → `subscription` в Kafka → оркестрация → свежие чтения из content-нити → API → живой график в кабинете покупателя |

## Маппинг практик базового уровня (фасад)

Базовый уровень не строит пайплайн, а **пользуется** маркетплейсом — тем же фасадом, который видят продвинутые.

| Лекция | Сценарий на витрине «Спутник Данные» |
| --- | --- |
| 1. Введение + Python | Регистрация покупателя, прогулка по витрине каталога; первый Python открывает образец CSV датчиков |
| 2. Python | Циклы/условия/функции над JSON «мои заказы/подписки» из личного кабинета |
| 3. Данные и pandas | Купленный датасет за месяц: CSV/JSON/Parquet, dtypes, сравнение форматов |
| 4. Простой сбор | Первый REST-запрос к `GET /api/v1/datasets`, выгрузка образца; лицензии/этика на странице условий |
| 5. Базовая очистка | «Грязный» датасет датчиков (пропуски/дубли); сверить с рейтингом качества карточки |
| 6. Предобработка | Фильтрация по станциям, группировка, temp→°C — приведение к схеме из документации |
| 7. SQL/хранение | Личный архив в SQLite «мои купленные данные»; запросы как у каталога внутри портала |
| 8. Визуализация | Дашборд покупателя: динамика температуры/PM2.5 по подпискам; итоговый мини-проект |

## Что выигрываем

- **Один мир вместо двух.** Не нужно отдельно объяснять «продвинутый пример» и «базовый пример» — это один портал с фасадом и машинкой.
- **Сквозная история получает смысл-кульминацию.** Итог семестра — *реальная покупка данных покупателем*, и данные в ответ *физически едут по конвейеру*.
- **Тема «качество данных» обретает дом.** Рейтинг качества на карточке товара = результат валидации и профилирования; отзывы о качестве данных = NLP-корпус. Оба уровня говорят об одном и том же.
- **Практики перестают быть разрозненными примерами.** Каждый элемент фасада — овеществлённое понятие курса, видимое на экране.

---

## План реализации

1. **Фасад (фронт/базовый уровень):** витрина каталога + карточки датасетов + кабинет + Swagger + пара живых графиков. Тянет данные из API.
2. **Content-нить:** эмулятор датчиков (Kafka producer или REST) → MinIO bronze → валидация → silver → ClickHouse gold.
3. **Commerce-нить:** микродвижок витрины генерирует `click/order/subscription/download/review` в Kafka.
4. **Оркестрация:** Airflow связывает подписку и доставку чтений.
5. **Quality/observability + CI/CD + GDPR** на обеих нитях.

Всё — в одном открытом репозитории под `docker compose`; студенты читают код, а не пишут с нуля (как уже заложено в семинарах).

## Открытые вопросы

- Финальное имя/бренд («Спутник Данные», «СенсорХаб» — на выбор под стиль курса).
- Эмуляция потоков: скрипт-генератор (Kafka producer / фейковый MQTT), чтобы не зависеть от железа.
- Какие 2–3 вертикали продуктовых данных брать (метео + качество воздуха обязательно; транспорт/энергия опционально).
- Синхронизация с [[Семинары — Сквозной пайплайн]]: единая легенда «Спутник Данные» вместо двух миров.
