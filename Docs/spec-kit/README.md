# GitHub Spec Kit — «Спутник Данные»

> Пакет спецификационных документов проекта. Работает по принципам SDD
> (Specification-Driven Development): сначала контракты, потом код.
> Исходник-источник требований — [[../ТЗ — Демо-портал маркетплейса данных (SDD)]].

## Что это

Набор документов, которые живут в GitHub-репозитории проекта и определяют
**что** строим и **почему так**, до написания реализации. Каждый документ отвечает
за свой вопрос: открытые решения зафиксированы в ADR, API и события — в
машинных контрактах (OpenAPI/AsyncAPI), правила согласованы в конвенциях.

## Структура репозитория

```
.
├── specs/                       # машинные контракты (as code)
│   ├── openapi-catalog.yaml
│   ├── openapi-order.yaml
│   ├── openapi-delivery.yaml
│   ├── asyncapi-commerce.yaml
│   └── asyncapi-content.yaml
├── docs/                        # этот spec kit (человекочитаемые спеки)
│   ├── README.md                # ← вы здесь
│   ├── adr/                     # Architecture Decision Records
│   ├── contracts/               # конвенции API и событий
│   └── acceptance.md, milestones.md ...
├── src/                         # код (появляется после приёмки контрактов)
├── docker-compose*.yml          # профили base / adv / demo
└── .github/workflows/           # CI: валидация контрактов + тесты
```

## Как документы связаны

| Документ | Вопрос, на который отвечает |
| --- | --- |
| `specs/*.yaml` | Точный REST/событийный контракт каждого сервиса |
| `contracts/api-conventions.md` | Общие правила API: auth, ошибки, пагинация, rate-limit |
| `contracts/event-conventions.md` | Общий конверт события, топики, гарантии |
| `contracts/data-contracts.md` | Общие схемы (продукт, чтение, заказ) |
| `adr/` | Зафиксированные решения и отклонённые альтернативы |
| `acceptance.md` | Чек-лист приёмки каждого сервиса |
| `milestones.md` | Дорожная карта M0–M4 |

## Рабочий процесс (contract-first)

1. Изменение требуется → описать контракт в `specs/*.yaml` (или ADR для решения).
2. `make contracts` валидирует спеки (OpenAPI/AsyncAPI-линтеры) в CI.
3. Код реализует контракт; тест-контракт (`schemathesis`/подобное) гоняется по
   живым сервисам.
4. Ломающий контракт PR без сопровождающей правки кода — CI блокирует деплой.

> Живой статус и открытые вопросы — в разделах `## Открытые вопросы`
> исходного ТЗ. Решения по ним переносятся сюда в `adr/` по мере принятия.
