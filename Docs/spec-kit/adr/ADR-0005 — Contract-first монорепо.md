# ADR-0005 — Contract-first монорепозиторий с профилями запуска

- **Дата:** 2026-09-07
- **Статус:** Принят

## Контекст

ТЗ (§3) фиксирует один `docker compose` и профили `base` / `adv` / `demo`.
§13: как устроен репозиторий и как спецификации связаны с кодом. Нужна модель,
при которой контракты правятся до кода и CI блокирует несовместимость.

## Решение

**Один монорепозиторий**, где `specs/` — источник истины (contract-first):

- `specs/*.yaml` — OpenAPI/AsyncAPI каждого сервиса.
- `docs/` — этот spec kit: ADR, конвенции, приёмка, milestones.
- `src/<service>/` — код; реализация обязана соответствовать `specs/`.
- Профили запуска управляются env/docker-compose overlay, не кодом:

```bash
docker compose --profile base up      # фасад без Kafka/ClickHouse/Airflow
docker compose --profile adv up       # полный стек
docker compose --profile demo up      # adv + готовый репозиторий данных
```

CI (GitHub Actions): валидация контрактов (`openapi-generator` lint / AsyncAPI
CLI) + контрактные тесты против живых сервисов; PR, ломающий контракт без правки
кода, блокируется.

## Последствия

- Каждый сервис имеет пару «спека + папка кода», легко сопоставлять.
- Модель SDD воспроизводима: практика «сначала контракт».
- Один источник для двух уровней курса (base и adv читают один и тот же репозиторий).
