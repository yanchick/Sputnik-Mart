# Quickstart — проверка и запуск: Демо-портал «Спутник Данные»

Руководство для валидации фичи `001-sputnik-data-portal`. Содержит только команды запуска, шлюзы качества и сквозные проверки; реализация сервисов, миграции и полные тест-сьюты здесь не описываются. Детали контрактов — в [`contracts/`](./contracts/), сущностей — в [data-model.md](./data-model.md), требований — в [spec.md](./spec.md).

## Предварительные требования

- Docker Engine и Docker Compose v2 (профили `base`/`adv`/`demo`).
- `uv` для установки Python-зависимостей и запуска инструментов (Python 3.12).
- Свободные порты фасада, Postgres, Redis, а для `adv`/`demo` — также Redpanda, ClickHouse, MongoDB, MinIO, Airflow.
- Обычный ноутбук без специального оборудования (не-цели: продакшн-нагрузка и enterprise-HA).

## Запуск одной командой

| Профиль | Назначение | Команда |
| --- | --- | --- |
| `base` | только фасад: витрина/каталог/заказы/доставка + Postgres, генератор готовых датасетов | `docker compose --profile base up` |
| `adv` | полный стек: base + content plane, Redpanda, MinIO, ClickHouse, MongoDB, Airflow | `docker compose --profile adv up` |
| `demo` | как `adv`, но с предзаготовленным репозиторием данных для быстрого показа | `docker compose --profile demo up` |

После старта фасад доступен в браузере, Swagger/OpenAPI UI — через `api-gateway`. Базовый профиль должен быть готов не более чем за 5 минут (SC-001).

## Шлюзы качества

```bash
# зависимости и окружение
uv sync

# линт, форматирование, типы
uv run ruff check .
uv run black --check .
uv run mypy .

# unit-тесты
uv run pytest tests/unit

# контрактные тесты против живых сервисов (нужен поднятый стенд)
uv run schemathesis run specs/001-sputnik-data-portal/contracts/openapi-catalog.yaml --base-url http://localhost:8001/api/v1
uv run pytest tests/contract

# интеграционные тесты (testcontainers: Postgres, Redis, ClickHouse, Redpanda, MinIO)
uv run pytest tests/integration

# валидация машинных контрактов
# OpenAPI/AsyncAPI-линтеры и контрактные тесты гоняются в CI и блокируют выпуск при провале
```

Выпуск блокируется при несоответствии контрактов или провале автоматических проверок (FR-031, SC-010).

## Сквозные сценарии валидации

Все сценарии выполняются на указанном профиле. Ожидаемый результат сформулирован в терминах требований [spec.md](./spec.md).

### 1. US1 / SC-002 — витрина, покупка, кабинет (профиль `base`)

1. Войти под предсозданным демонстрационным аккаунтом.
2. Открыть каталог, применить фильтры по категории и минимальному рейтингу, открыть карточку датасета.
3. Убедиться, что карточка показывает описание, схему полей, объём, частоту, цену, лицензию и рейтинг качества.
4. Попытаться скачать неоплаченный датасет — ожидается отказ в доступе.
5. Оформить заказ с `Idempotency-Key`, повторить тот же запрос — дубль заказа не создаётся.
6. Скачать датасет в выбранном формате (CSV/JSON/Parquet) — данные отдаются, запись появляется в истории скачиваний.
7. Оставить два отзыва (оценки 1–5) — в рейтинг идёт только последний отзыв.
8. Проверить постраничную выдачу и единый формат ошибок с `requestId`.

**Ожидается**: путь «вход → покупка → скачивание» проходится не более чем за 3 минуты (SC-002); отказ без оплаты (FR-007); идемпотентность (FR-006); единые форматы (FR-034).

### 2. US2 / SC-003…SC-005 — путь данных датчиков (профиль `adv`)

1. Запустить `sim.sensors` с фиксированным `seed` и `sim.dirty` для контролируемого загрязнения.
2. Убедиться, что валидные чтения доходят от `sensor-gateway` до bronze → silver → gold.
3. Проверить, что битые записи попадают в `sensors.readings.dlq` и **не** появляются в silver.
4. Дождаться формирования отчёта качества с показателями пропусков, дублей, выбросов и аномалий.
5. Убедиться, что в silver нет дублей и пропусков, а витрина обновлена.
6. Повторить запуск генератора и DAG с тем же `seed`.

**Ожидается**: идентичный результат при одинаковом `seed` (SC-003); 100% невалидных записей в DLQ, 0% в silver (SC-004); 0 дублей при повторных прогонах (SC-005).

### 3. US2 / SC-008 — деградация и восстановление качества

1. Зафиксировать базовый `qualityScore` датасета в каталоге и на Quality-page.
2. Применить контролируемое загрязнение и завершить прогон.
3. Убедиться, что показатель качества снизился и виден на странице качества.
4. Очистить данные и завершить прогон.
5. Убедиться, что показатель вернулся к базовому, а `quality_score` в каталоге совпадает с отчётом.

**Ожидается**: деградация отображается и полностью снимается после очистки (SC-008, FR-020, FR-021).

### 4. US3 / SC-006 — подписка и живой поток (профиль `adv`/`demo`)

1. Оформить подписку с настраиваемым `intervalSec` — она становится `SUB_ACTIVE` и порождает событие `commerce.subscriptions`.
2. Подключиться к `GET /api/v1/streams/{subscriptionId}` (SSE) и убедиться в уникальности `id = readingId` у кадров.
3. Разорвать соединение и переподключиться — дубли не создаются.
4. Приостановить подписку (`SUB_PAUSED`) — живой поток и выборка новых данных прекращаются, доступ к купленным данным сохраняется.
5. Возобновить подписку — доставка продолжается без дублей.
6. Отменить подписку (`SUB_CANCELLED`) — подписка завершается, купленные данные доступны, можно оформить новую.

**Ожидается**: сквозной сценарий «подписка → живой поток → график» проходит за один прогон не более чем за 10 минут (SC-006); идемпотентность переподключения (FR-023).

### 5. US4 / SC-008, SC-009, SC-013, SC-014 — качество, безопасность, воспроизводимость

1. Искусственно ухудшить данные — на дашборде Grafana срабатывает алерт о деградации; доступны метрики лага и свежести.
2. Скачать выгрузку и выборочно проверить отсутствие PII (только маскированные значения).
3. Повторить генерацию с тем же `seed` и сравнить дайджест — результат идентичен.
4. Превысить лимит частоты — получить `429` с указанием времени повторной попытки.
5. Сделать запрос через несколько сервисов и найти все связанные журналы по `requestId`.
6. Открыть Quality-page и сверить показатели пропусков, дублей, выбросов и аномалий с рейтингом в каталоге.

**Ожидается**: срабатывает алерт деградации (SC-011); 0 случаев PII в выгрузках (SC-009); 100% PII удаляется по сроку (SC-013); 100% сверхлимитных запросов получают отказ с `Retry-After` (SC-014); трассировка по `requestId` (FR-027).
